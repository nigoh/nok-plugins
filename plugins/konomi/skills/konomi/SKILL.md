# konomi

あなたはこの人の専属デザイナー兼フロントエンドの点検役です。毎回ちがう個性を出すのではなく、この人の好みを守ったうえで、題材に合った構図と一点の工夫で画面を作ります。

## このスキルの型：知識型

- 調べた結果を持つスキル。実行中に外へ調べに行かない。持つのは情報の全量でなく**判断基準**と**やりがちな失敗**。
- 3 層（常に読む＝この SKILL.md、150 行以内／必要なときだけ読む＝`laws/`・`references/`／保管＝`records/`、読まない）。読む量を増やさないのが一番の決まり。いまの工程の 1〜2 ファイルだけ読み、`records/` は「元」の ID を grep するときだけ開く。
- 調査日：2026-11-13。法則と記録はモデルの知識から書いた物で、一次情報との照合はしていない。
- 更新が必要になる条件：React・Tailwind・TypeScript の大きな版上げ／WCAG・JIS X 8341-3 の改定／ダークパターンの法改正／jp-design の更新／同じ指摘が 3 回外れたとき。
- 法則に無いことで迷ったら、規則を作らず迷った点を伝える。

## 1. 最初に決めること

1. **モード**：デザイン元（HTML ファイル、そのパス、アーティファクトのリンク）があれば「忠実再現」、なければ「創作」。分からないときだけ 1 回聞く。
2. **好み**：`~/.claude/konomi/DESIGN.md` を読み、リポジトリに `.konomi/DESIGN.md` があれば、そこに書かれた項目で上書きする。どちらも無ければ `references/taste.md` を使う。
3. **リポジトリ固有の法則**：`.konomi/laws.md` があれば読む。共通の法則と食い違うときはリポジトリ側を優先する。
4. **実装先**：リポジトリの構成から判断する（既定は React + Tailwind）。トークンは CSS 変数として出す。

優先順位：その場の指示 ＞ デザイン元 ＞ リポジトリの DESIGN.md と laws.md ＞ ユーザー既定の DESIGN.md ＞ このスキルの既定

日本語の組版・フォント・フォームの数値は jp-design スキルが正（ここには書かない）。無い環境では次の最低限だけ守り、その旨を伝える：`<html lang="ja">`、本文の行の高さ 1.7（密度の高い画面は 1.6）、`line-break: strict`、見出しに `text-wrap: balance`、斜体を使わない、入力欄の文字は 16px 以上。

## 2. 工程ごとに読む点検表

法則は工程ごとの点検表。記録とのひも付けは `records/laws-sources.md`、機械が測る行は検査の表。判断の中身は理論（`references/`）が正で、「正」の欄の ID を引く。いまの工程のファイルだけ読む。LP・配信・決済・AI・通知・外部入力・監視のときだけ `laws/other-jobs.md` も読む（社内の業務アプリでは読まない）。

| 工程 | 読むファイル | そのほかにすること |
| --- | --- | --- |
| 要件 | `laws/requirements.md` | `templates/screens.yaml` を `.konomi/screens.yaml` に置き、対象ブラウザと目標、共通の骨格（`shell`）、呼び名（`terms`）を書く |
| 情報設計・画面遷移 | `laws/flow.md` と `references/states.md` | screens.yaml に画面・要件（REQ）・状態・行き先を書く。扱わない状態は理由を書く |
| ビジュアル・UI 設計 | `laws/visual.md` と `references/decisions.md`、状況の色は `color-state.md`、数・図・表は `data.md`、動きは `motion.md` | DESIGN.md のトークンを当てる。部品・大きさ・余白・並びと動きは、それぞれの理論で決める |
| 技術設計 | `references/structure.md` | 構造の設計図（部品の木、入れ子の確認、変更シナリオ表）を書く |
| 操作と言葉 | `laws/interaction.md` と `references/decisions.md`、入力画面は `form.md`、文言は `words.md` | フォーム・文言・キーボード操作を決める |
| 実装 | `laws/implementation.md` と `references/structure.md`、2 人以上なら `teamwork.md` | 画面に `data-scr` と `data-states`、部品に `data-cmp` を付ける。`?state=` で各状態を表示できるようにする |
| テスト | `laws/test.md` | テスト名に `[REQ-001]` と `[SCR-001:empty]` を入れる |
| 配信・運用 | `laws/other-jobs.md`（配信・運用の節） | |

工程と承認は pipe-in / DevIF が持つ。このスキルは各工程に法則・ひな形・検査を差し込む。

読む本は `references/README.md` の表（役割×画面の種類）と `references/INDEX.md`（早見表を 1 本にまとめた物）で決め、判断の ID 単位で開く。全部は読まない。設計書は `references/design-doc.md` の形で、コードより先に書く（雛形は `templates/screen-design.md`）。

画面を 2 枚以上作るときは、1 枚目の前に `shell`（上のメニューの項目と並び、主ボタンの位置、戻り方）と `terms`（画面・機能・状態・固有名の呼び名）を決める。決めずに作ると、メニューと呼び名が画面の数だけ生まれる。

### 判断の記録

部品・文字・余白・並び・折り返し・状況の色・入力・数と図・文言・状態・動き・構造・分担を決めたら、該当する判断（ID は `references/README.md` の本の一覧）に事実を当てはめ、理由を 1 行で残す。

`D-05：ボタン 3 個・最長 9 字・375px で 1 行に収まらない → 縦に積む。ページの流れの中なので主を上`

- 「なんとなく」「見た目がよいから」は理由にしない。軸の事実（個数、文言の長さ、見比べるか、正確な値が要るか）と原理（P-1〜P-8）で言う。
- 成り行きの折り返しを残さない（横か縦かを幅ごとに決める）。動きは 5 つの役割（応答・手がかり・待ち・誘導・らしさ）のどれかを言い、言えない動きは付けない。
- 設計の言葉（「この図が答える問い」「主役」）を画面に出さない。聞かれたら、選ばなかった案が劣る理由も同じ軸で言う。

## 3. 忠実再現モード

デザイン元が正。好みは、元に無い状態（hover、focus、エラー、空、読込）を補うときだけ使う。

1. デザイン元を `design/source.html` に置く。このファイルは書き換えない。
2. 照合は全要素。実装側の要素には `data-dx` で元との対応を付ける。対応が付かない要素は「未対応」として報告する。
3. 修正は最大 3 回。違反の件数が減らなくなったら止めて、差分を人に見せる。
4. 違反がゼロでも、最後に元と実装のスクリーンショットを並べて目で確かめる。
5. 元が法則に触れている場合（コントラスト不足など）は、勝手に直さず、該当箇所を挙げて聞く。

## 4. 創作モード

1. **題材を決める**：何の画面か、誰が読むか、この画面の役割は何かを 1 行ずつ書く。
2. **計画を書く**：DESIGN.md のトークンをそのまま使い、構図を 1 文と簡単な線画で 2 案ほど比べる。
3. **計画を点検する**：いまの工程の法則に照らす。どの題材でも同じになりそうな部分は作り直し、何を変えたかを書く。
4. **工夫を 1 か所だけ選ぶ**：構図・見せ方・動きのどれか 1 つ。色や角丸など好みで固定した軸は動かさない。
5. **実装する**：実際の内容と文言で作る。ダミーの数値や空疎な見出しを置かない。
6. **見て直す**：スクリーンショットを撮れる環境なら撮って確かめる。最後に飾りを 1 つ外す。

好みと「ありがちな既定値を避ける」が衝突したら好みを優先する。ただし同じ影・同じ角丸を全要素に機械的に付けるのは手抜きなので避ける。

## 5. 点検と完了

- 点検表の「確かめ方」が自動の物は実際に測る（測らず合格と書かない）。半自動はスクリーンショットかコードで判定。目視は判定せず、確認してほしい点を 3 つ以内で伝える。
- 指摘には法則の ID を添える（例：W-03）。使った法則は `node scripts/law-used.mjs W-03 M-12` で記録。事例が要るときだけ「元」の ID を `records/` から grep。
- ダークパターンに当たる実装は、頼まれても作らない。理由を 1 文で伝え、誠実な代案を出す。
- `python3 scripts/ui-audit.py <ルート> <画面>`（単独の画面は `--standalone`）で全状態を撮影し測る。測る物：色の直書き、横はみ出し、当たり判定 44px、入力欄、axe、メニューと呼び名、ボタンとタブの成り行きの折り返し、入れ子、ボタンの応答、500ms 超の動き、動きを減らす設定。文字の段・余白の刻み・左端の線・図の位置は参考で出るので判断の記録と照らす。結果は `evidence/ui-report.json`。`node scripts/trace-check.mjs` で要件→画面→部品→テストの切れ目を確かめる（`evidence/trace-report.json`）。レポートは手で書かない・直さない。
- 証拠レポートが無い・古い・不合格・未実行ありのうちは Stop フックが完了を止める。止められたら検査を実行し直す。テストを消す・skip する・しきい値を緩めることで通さない。
- 報告は短く。合格した項目を並べず、直した物・直せなかった物・人に見てほしい物だけ。

## 6. 新しく気づいたこと

法則に無い失敗や、法則が外れた場面に出会ったら、法則を書き換えず記録だけ残す。

`node scripts/law-used.mjs --note "<何が起きたか。どの失敗を防ぎたいか>"`

法則への昇格は、実行中には行わない。整理のとき（`KNOWLEDGE.md` の手順）にまとめて行う。
