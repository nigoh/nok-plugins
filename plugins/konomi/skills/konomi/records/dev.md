# 作り手側のアンチパターン集

要件・設計・実装・テスト・配信の各工程で、作り方そのものを点検するための一覧。利用者から見える問題は `anti-patterns.md` にある。

- **検出**の読み方：`自動` は括弧内の道具で実際に測る。`半自動` は成果物やコードを読んで一次判定する。`目視` は人が判断するので、確認依頼として伝える。
- 「要確認」と書かれた規則名・仕様・法令は、使う前に一次情報で確かめる。
- E は工程の前半（要件・設計）、F はコード、G は安全・テスト・配信で使う。

## E1 要件

| ID | アンチパターン | なぜ困るか | 検出 | 直し方 |
| --- | --- | --- | --- | --- |
| E1-01 | 機能ごとの受け入れ基準が無く「いい感じに動く」で着手 | 完了の判断が人によって違い、手戻りと終わらない確認が発生する | 半自動 | 各機能に「前提・操作・期待結果」の形式で検証可能な基準を3件以上書く |
| E1-02 | 画面の状態（初期・読み込み中・空・エラー・部分失敗・権限なし）が列挙されていない | 正常系だけ作られ、異常時の表示が実装者の想像任せになる | 半自動 | 画面ごとに状態一覧表を要件に含め、各状態の表示内容を決める |
| E1-03 | 対象ブラウザ・OS・端末・画面幅が未定義 | 検証範囲が決まらず、公開後に特定環境の不具合報告が出る | 半自動 | 対象環境の一覧（最低バージョン・最小幅を含む）を要件に明記する |
| E1-04 | 性能目標（表示完了時間、操作応答、バンドルサイズ）が無い | 遅いかどうかの基準が無く、劣化に気づけないまま出荷される | 半自動 | LCP・INP・初回JS容量などの数値目標を決め、計測条件（回線・端末）も書く |
| E1-05 | アクセシビリティの目標水準が未定義 | 対応の深さが担当者次第になり、後から全面改修が必要になる | 半自動 | 準拠する水準（例: WCAG 2.2 AA。日本では JIS X 8341-3:2016 の適合レベル表記も併記するか要確認）と対象範囲を要件に書く |
| E1-06 | 画面上の文言・エラー文・空状態の文が未決定のまま実装 | 仮文言が本番に残り、後で文言変更が全画面に散らばる | 半自動 | 文言一覧を要件に添付し、未決は「要確認」として残して出荷前に消し込む |
| E1-07 | 「既存画面と同じ」「他社サービスのように」で仕様を済ませる | 参照先の解釈が人により違い、再現すべき挙動の漏れが出る | 半自動 | 参照元の挙動を項目に書き下ろし、踏襲しない点も明記する |
| E1-08 | データ量の前提が無い（件数、文字数、画像サイズ） | 100件で作った一覧が1万件で破綻し、設計をやり直す | 半自動 | 想定の平均値と最大値を要件に書き、最大値での表示方針（ページ分割等）を決める |
| E1-09 | 権限・ロールごとの見え方と操作可否が未定義 | 権限の抜けが実装後に発覚し、画面と API の両方を直すことになる | 半自動 | ロール×機能の可否表を作り、見せない・無効にする・隠すの別も決める |
| E1-10 | 成功を測る指標とイベント計測の定義が無い | 作った後に効果を判断できず、計測の後付けで画面を再改修する | 半自動 | 目的指標と必要なイベント名・発火条件を要件に書く |
| E1-11 | 対応言語・地域・日時の扱い（タイムゾーン、表記）が未定義 | 日付ずれや文字あふれが公開後に見つかる | 半自動 | 対応ロケールと日時の保持形式・表示形式を要件で決める |
| E1-12 | 非機能の制約（オフライン、通信断、再試行、同時編集）に触れていない | 通信失敗や競合時の挙動が場当たりになる | 半自動 | 通信失敗・同時操作の想定ケースを列挙し、期待挙動を一行ずつ書く |
| E1-13 | 完了の定義（テスト範囲、レビュー、文書）が無く範囲が曖昧 | 「できた」の認識がずれ、追加作業が無償で膨らむ | 目視 | 完了条件のチェックリストを合意し、範囲外も明記する |
| E1-14 | 入力項目ごとの文字種・桁数・必須・形式の検証規則が未定義 | 全角半角や桁数の扱いが実装者任せになり、画面と API で判定が食い違う | 半自動 | 項目表に文字種・最大最小長・形式・正規化の方針を書き、画面とサーバーで同じ規則を使う |
| E1-15 | 個人情報の取得項目・利用目的・外部送信の有無が整理されていない | 同意文言や計測タグの要否が後から発覚し、画面と実装をやり直す | 目視 | 取得項目と送信先を一覧にし、同意や告知が要る箇所を要件に入れる（関連法令は要確認） |

## E2 設計とデザインの引き渡し

| ID | アンチパターン | なぜ困るか | 検出 | 直し方 |
| --- | --- | --- | --- | --- |
| E2-01 | 画面一覧が無く、画面の抜けに実装中に気づく | 見積と進捗が崩れ、後から画面が増える | 半自動 | 全画面のIDと名前の一覧を作り、ルート定義と突き合わせる |
| E2-02 | 画面遷移図が無く、遷移条件と戻り先が不明 | 戻る操作や直リンク時の挙動が実装者の推測になる | 半自動 | 遷移図に条件・戻り先・直リンク時の扱いを書き込む |
| E2-03 | 状態表が無く、画面の状態ごとの見た目が決まっていない | 空・エラー・読み込み中の画面が場当たりで作られる | 半自動 | 画面×状態の表を作り、各セルにデザインか方針を埋める |
| E2-04 | デザイン元にホバー・フォーカス・無効・エラーのバリアントが無い | 実装者が独自に補完し、見た目が部品ごとにばらつく | 半自動 | 部品ごとに全状態のバリアントを用意してから引き渡す |
| E2-05 | 色・余白・文字サイズ・角丸などのトークン定義が無いまま実装 | 値が直書きで散らばり、ブランド変更や暗色対応で全箇所を直す | 半自動 | トークン表（名前と値）を先に決め、Tailwind のテーマ（v3 は設定ファイル、v4 は CSS の @theme）へ写してから実装する |
| E2-06 | トークンがデザイン側と実装側で別の値・別の名前になっている | 見た目が微妙にずれ、修正のたびに照合が必要になる | 半自動 | トークンの単一の正本を決め、片方から生成するか差分検査の自作スクリプトを置く |
| E2-07 | レスポンシブの方針（ブレークポイント、並べ替え、折りたたみ）が未定 | 幅ごとの崩れが実装者判断になり、確認漏れが出る | 半自動 | 主要な幅3段階以上の見え方を画面ごとに指定する |
| E2-08 | デザインが短い理想データだけで作られ、実データで検証していない | 長い名前・多い件数・欠損値でレイアウトが崩れる | 半自動 | 最長・最短・欠損・最大件数の実データ相当の例でデザインを確認する |
| E2-09 | コンポーネント名がデザインと実装で違う | 会話と検索が噛み合わず、重複実装や取り違えが起きる | 半自動 | 命名規則を共有し、対応表を置くか名前を揃える |
| E2-10 | 操作の振る舞い（アニメ、遷移時間、キーボード操作）が静止画だけで指定されている | 動きと操作性が実装者任せになり、後で指摘が集中する | 半自動 | 動き・フォーカス移動・キー操作を注記かプロトタイプで指定する |
| E2-11 | アイコン・画像の書き出し形式と版が管理されていない | 画質不一致やファイル重複、更新漏れが起きる | 半自動 | 書き出し規則（形式・サイズ・置き場所）を決めて一覧化する |
| E2-12 | 設計の決定事項と理由が残らない（口頭・チャットのみ） | 後から理由が分からず、同じ議論の蒸し返しと不整合修正が起きる | 目視 | 決定事項を短い記録として一箇所に残し、画面一覧からリンクする |
| E2-13 | データ構造（APIの項目、必須・任意、型）が画面設計と別々に決まる | 画面が必要とする項目が API に無いと分かり、両側で作り直す | 半自動 | 画面ごとの必要項目とAPI項目の対応表を作り、不足を事前に洗い出す |
| E2-14 | フォーカス順・読み上げ順・見出し構造が設計に含まれていない | キーボードや読み上げで使えない画面が実装後に見つかる | 半自動 | 画面ごとにフォーカス順と見出し階層、主要領域の区切りを設計図に注記する |

## E3 コンポーネント設計

| ID | アンチパターン | なぜ困るか | 検出 | 直し方 |
| --- | --- | --- | --- | --- |
| E3-01 | 数百行超の巨大コンポーネントに表示・取得・変換が同居 | 読めず、変更の影響範囲が分からず、テストが書けない | 自動（ESLint の `max-lines` / `max-lines-per-function`、`complexity`） | 取得・整形・表示を分け、行数と複雑度の上限を ESLint に設定する |
| E3-02 | props が10個を超える部品 | 呼び出し側が読みにくく、組み合わせの不整合が生まれる | 半自動 | 関連する props をまとめるか、合成（children・スロット）に切り替える |
| E3-03 | boolean props の乱立（`isPrimary` `isLarge` `isDanger` 等） | 矛盾する組み合わせが作れてしまい、状態が爆発する | 半自動 | `variant` と `size` の列挙型に置き換え、型で矛盾を排除する |
| E3-04 | 見た目と振る舞い（取得・業務判断）が一つの部品に密結合 | 見た目だけ再利用できず、状態別の表示確認も難しい | 半自動 | 表示専用の部品と、データを渡すコンテナを分離する |
| E3-05 | 制御と非制御が混在（`value` と `defaultValue` を同時に受ける、途中で切り替わる） | 入力が反映されない、警告が出る、挙動が読めない | 半自動（React の開発時警告を拾うテストで検出。静的には限定的） | どちらかに統一し、両対応するなら切替を型で表現して途中変更を禁止する |
| E3-06 | 似た部品の重複（ボタン、モーダル、カードが画面ごとに別実装） | 修正が全箇所に必要になり、見た目とアクセシビリティが揃わない | 半自動 | 重複を洗い出して共通部品に集約し、置き場所と命名を決める |
| E3-07 | 過度な汎用化（使用箇所1つのために設定項目だらけの部品） | 使い方が難しく、変更で全利用側が壊れる | 目視 | 利用が3箇所前後になるまで具体実装に留め（目安）、重複が見えてから抽出する |
| E3-08 | 状態別（空・読み込み・エラー）の表示を単独で確認できない構造 | 異常系の見た目が検証されず、不具合が出荷後に見つかる | 半自動 | データを props で受ける表示部品にし、Storybook 等で状態ごとの例を用意する |
| E3-09 | props のバケツリレー（5階層以上の素通し） | 中間部品が無関係な props を抱え、変更が連鎖する | 半自動 | 合成で子を直接渡すか、局所的な Context に切り出す |
| E3-12 | 利用側に `any` や過広の型を許す props 定義 | 誤った渡し方が型検査をすり抜ける | 半自動（tsc の `strict` と ESLint の `@typescript-eslint/no-explicit-any` で any は拾えるが、過広の型は読んで判定） | 厳密な型を定義し、判別可能なユニオンで組み合わせを表現する |
| E3-14 | スタイル指定が部品の外から上書き前提（`className` の上書き頼み、`!important`） | 詳細度の競合で見た目が予測できなくなる | 半自動（stylelint の `declaration-no-important` は CSS のみ。Tailwind の `!` 接頭辞は grep する自作スクリプト） | バリアントで公開する見た目を限定し、上書きは意図した口だけに絞る |
| E3-15 | モーダル・メニュー・タブなどを自作し、フォーカス管理や Esc での閉じ方が抜ける | キーボードと読み上げで操作できず、背面の操作も可能なままになる | 半自動（axe や Playwright のキー操作テストで一部検出） | 実績のある部品ライブラリか標準要素（dialog 等）を使い、フォーカスの閉じ込めと復帰を確認する |

## E4 状態管理・データ取得

| ID | アンチパターン | なぜ困るか | 検出 | 直し方 |
| --- | --- | --- | --- | --- |
| E4-01 | サーバー由来のデータを全てグローバルストアに置いて手動で同期 | 更新漏れと二重管理で古い表示が残る | 半自動 | サーバー状態は TanStack Query や SWR などの取得層に任せ、ストアはクライアント固有の状態に限る |
| E4-02 | 派生値を別の state に二重保持（合計、絞り込み結果、件数） | 元データとずれて表示が食い違う | 半自動 | 元データから描画時に計算し、重いときだけ `useMemo` を使う |
| E4-03 | 更新後にキャッシュ無効化・再取得をしない | 保存したのに一覧が古いままになる | 半自動 | 更新成功時に関連クエリを無効化するか、レスポンスでキャッシュを更新する |
| E4-04 | 楽観更新の失敗時に巻き戻しが無い | 保存失敗なのに画面だけ成功のまま残り、利用者が誤認する | 半自動 | 更新前の値を保持して失敗時に戻し、失敗を利用者へ通知する |
| E4-05 | 古い応答が新しい応答を上書きする競合（連続検索、画面遷移直後） | 最後に入力した内容と違う結果が表示される | 半自動 | `AbortController` で前の要求を中止するか、取得層の依存キーに任せる |
| E4-06 | 読み込み中・エラーを握りつぶす（空の `catch`、エラー時に空配列を返す） | 失敗が「データなし」に見え、原因調査もできない | 自動（ESLint の `no-empty`）＋半自動（空配列フォールバックはコード読み） | エラーを状態として保持して画面に出し、空と失敗を区別する |
| E4-07 | 絞り込み・並び順・ページ・選択タブなどを URL に持たない | 再読み込み、共有、戻る操作で状態が失われる | 半自動 | 共有・復元したい状態をクエリパラメータやパスに持たせる |
| E4-08 | 親子で順番に取得してウォーターフォールになる | 表示までの時間が各要求の合計になる | 半自動 | 依存の無い取得は並列に開始し、先読みやルーター側のローダーで早める |
| E4-09 | 一覧の各行から個別に詳細を取得する（N+1） | 要求が件数分に増え、遅く、サーバー負荷も上がる | 半自動 | 一覧用の一括取得に必要項目を含めるか、まとめて取得する API を用意する |
| E4-10 | 取得の依存値（検索語、ID）が変わっても再取得されない、または不要に毎回再取得する | 表示が古い、あるいは無駄な通信が走る | 自動（ESLint の `react-hooks/exhaustive-deps`、取得層のキー設計は半自動） | 取得キーに依存値を全て含め、不要な再取得は `staleTime` で抑える |
| E4-11 | 入力のたびにAPIを呼ぶ（デバウンス・最小文字数なし） | 通信量と競合が増え、遅く不安定になる | 半自動 | デバウンスと最小文字数を設け、前の要求を中止する |
| E4-12 | フォーム入力の一時値までグローバルに置く | 画面離脱後も残り、他画面へ漏れて再描画範囲も広がる | 半自動 | 入力中の値は画面内のローカル state かフォームライブラリに閉じる |
| E4-13 | 二重送信の防止が無い（送信中も押せる、冪等性なし） | 同じ登録が重複して作られる | 半自動 | 送信中は操作を無効化し、可能ならサーバー側で冪等キーを使う |
| E4-15 | 認証切れ（401）の扱いが各所で個別実装されている | 画面ごとに挙動が違い、入力中のデータが失われたり無限に再試行されたりする | 半自動 | 取得層の共通箇所で認証切れを捕捉し、再ログイン導線と入力保持の方針を一箇所に置く |

## F1 React

| ID | アンチパターン | なぜ困るか | 検出 | 直し方 |
| --- | --- | --- | --- | --- |
| F1-01 | effect で props や state から派生値を計算し別 state に同期 `useEffect(() => setB(f(a)), [a])` | 余計な再レンダーが走り、一瞬古い値が表示される | 半自動 | レンダー中に計算するか、重ければ useMemo にする |
| F1-02 | 依存配列を eslint-disable で黙らせる、または空配列で逃げる | 古い値を閉じ込めたまま動き、更新が反映されない | 自動（ESLint react-hooks/exhaustive-deps。disable コメントは grep） | 依存を正しく列挙し、必要なら処理を effect の外や useEffectEvent 相当に切り出す（版要確認） |
| F1-03 | リストの key に配列 index を使う | 並べ替えや削除で入力値や開閉状態が別の行に残る | 半自動（ESLint react/no-array-index-key で候補抽出、静的リストは許容） | 項目固有の安定 ID を key にする |
| F1-04 | レンダー中の副作用（fetch、ストレージ書き込み、乱数や現在時刻での表示） | 二重実行や SSR との不一致で表示がちらつき、警告が出る | 半自動 | 副作用はイベントハンドラか effect に移し、乱数や時刻は state か props で渡す |
| F1-05 | memo 化した子や Context の value に毎回新しいオブジェクトや関数を渡す | memo が効かず、Context の全消費者が毎回再レンダーされる | 半自動（Context value のみ ESLint react/jsx-no-constructed-context-values で自動） | 安定参照にするか、状態を子側へ寄せて渡さずに済ませる |
